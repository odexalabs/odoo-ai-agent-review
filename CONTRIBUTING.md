# Contributing

Thank you for helping. agent-review is small, and it makes claims about evidence, so contributions are held to
one rule above the usual ones: **a report may only say what the recorded evidence supports.** "Could not
observe" is a result, never a zero or a clean pass.

## Reporting a bug

Open an issue with:

- what you ran (the command, the scenario, the run profile with paths and passwords removed);
- your Odoo version and edition, PostgreSQL version, Python version and operating system;
- what the **redacted** report said (`summary.txt`), after you have read it for business values you cannot share;
- what you expected instead.

**Never attach** a `run.json`, a `raw_diff.json`, an Odoo log, an `odoo.conf`, a `standin.jsonl` or anything else
from a run directory: they are the private record of the run and can hold conversation text, record values and
connection details. Describe what they show instead.

A suspected security problem goes privately, not to an issue: see [SECURITY.md](SECURITY.md).

## Changing the code

```bash
pip install -e ".[dev]"
ruff check .
pytest
```

- **Tests come in tiers** (`tests/conftest.py`). The default tier is pure Python and is what CI runs. The
  `integration` tier needs PostgreSQL and the synthetic fixture templates (`AGENT_REVIEW_INTEGRATION=1`); the
  `odoo` tier also starts real Odoo processes (`AGENT_REVIEW_ODOO=1`). Say which tiers you ran, with pass AND skip
  counts.
- **A guarantee gets an attack, not only a happy path.** If you add or change something the documentation
  promises (a credential cannot leak, mail cannot leave, a template cannot be dropped, a value is withheld from the
  report), add a test that tries to break it, and check that the test fails when the protection is removed.
- **Nothing is inferred from prose.** Report classification is by rules the operator writes; attribution only
  where recorded evidence covers the boundary.
- **Do not add Odoo source or Odoo's own message text** (in code, tests or docs). Refer to Odoo code by file and
  method name; use invented text in tests. Operators supply the exact messages their deployment shows through
  `report_rules`. The one Odoo-specific text the tool depends on is the format of the log lines the Odoo 19
  driver parses. Supporting another format needs a reviewed fixture of it (synthetic lines, never a real log) and
  regression tests showing what the parser reads from it and that a log it cannot read completely stays
  unobservable, with unknown usage.
- **Scenarios** must be synthetic. An UPDATE key's allowed fields should come from a scripted reference write
  through Odoo's own tool, not from reading the code.
- The sample report in `examples/` is regenerated by its script; a change to the report format regenerates it in
  the same pull request (a test checks this).
